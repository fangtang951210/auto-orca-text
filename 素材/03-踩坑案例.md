# 踩坑实录(2026-10-27/28 真实案例,全部亲历)

## 坑 1:手工拼装编排流程,四连败
- **错误做法**:不读官方 skill,看着 --help 的参数名自己拼了四步(launch → task-create → dispatch --inject → terminal send 喂话术),每个参数值靠想象填(`--from worker` 这种自造身份)
- **结果**:完工报告连发三封全被系统拒收;协调者干等一个永远不会来的回执
- **为什么错**:绕过官方协议,用想象填补参数;--help 只给参数名不给协议
- **正确做法**:读 `orca skills get orchestration` 全文,按 canonical loop 用 worker-start 一条龙(生命周期 ID 由系统注入,不需要也不允许自造)。改用官方姿势后一次通过。

## 坑 2:自制轮询 Monitor,信到了没抓到
- **错误做法**:不信任官方等待,自己写 Monitor 轮询 inbox,grep 模式盯 task/dispatch ID
- **结果**:inbox 消息行里根本没有这些字段,工人回执到了,轮询脚本没匹配到,协调者误判"工人没干活"
- **为什么错**:对消息格式做格式假设;官方 check --wait 从不需要知道格式
- **正确做法**:check --wait 阻塞等待,零格式假设

## 坑 3:把"返回值"当"事实"
- **错误做法**:worker-start 返回 taskId 就当工人活了;terminal read 的一次快照("Meandering 42s")当"正在执行"
- **结果**:对着一个已经干完退场的工人空等;对着一个根本没跑起来的 agent 说"流程符合预期"
- **为什么错**:启动类命令的成功返回 ≠ 世界真的变成它声称的样子
- **正确做法**:启动后必验证(terminal list 看新终端/读屏);判断"完成"用三层证据(回执 + git diff + worker-show.state)

## 坑 4:skill 被 grep 一角就动手
- **错误做法**:213 行的官方 skill 只 grep 了 worker_done 片段就开始拼命令
- **结果**:漏掉 canonical loop、角色路由、工人义务全部关键条款
- **正确做法**:全文通读;根治方案见 04-门禁设计.md(机械强制:动作命令无"全文通读登记"直接拦)

## 坑 5:folder 项目硬开编排围挡
- **错误做法**:`worker-start --worktree new-child` 直接用在 folder 型项目上
- **结果**:invalid_argument(Folder projects cannot create orchestration worktrees)
- **正确做法**:两步法(先 orca worktree create 建围挡,再 worker-start --worktree id:完整id)

## 坑 6:工人干完退场,终端变"空 shell"
- **现象**:启动后 20 秒读终端,只有 shell 提示符,没有 claude 痕迹,疑似没起来
- **真相**:工人干完即退场(quick 任务),终端回到空闲 shell;此时应查 worker-show(state=succeeded)+ 回执 + git,而不是断定失败
- **教训**:"空"可能是"已结束",用 dispatch 状态说话

## 坑 7(环境类):GitHub 间歇全断
- 现象:gh/ssh 22/ssh 443 全部被代理层 reset(fake-ip 198.18.x.x),数分钟后自愈
- 处理:不硬莽;先走不依赖网络的部分,通道恢复再推

## 坑 8(历史遗留,教学法案例):同名 worktree 自动避让
- `worktree create --name isolation-demo` 第二次使用时,Orca 自动起名 isolation-demo-2,不留神会以为建错了
